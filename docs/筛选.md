# 筛选

本手册记录把动态 trace 收敛成“纯转发 / 真实实现”候选时使用的判据。

## 1. 反汇编字段可信度

> 当前 `disasm.json` 来自带 `-finstrument-functions-after-inlining` 和
> coverage 的构建。`size` / `instructions` 包含插桩与 coverage 指令；
> `calls` 包含 `__cyg_profile_func_*` 调用；`real_calls` 已扣除这些钩子。
> 下表按可信度从高到低排列；当前所有字段都已写入
> `functions[].disasm`。

可信度定义：

- **高**：接近函数内部逻辑，可以直接作为主判据；
- **中高**：有明确偏差或依赖启发式，适合相对比较和组合判断；
- **中**：受插桩、coverage、编译器生成代码影响较大，只能辅助；
- **中低**：多类信号混在一起，单独使用容易误判；
- **低**：主要反映插桩污染，不能代表函数逻辑。

| 字段                                | 说明                                                   | 为什么可信 / 不可信                                                             | 可信度    | 现状  |
| --------------------------------- | ---------------------------------------------------- | ----------------------------------------------------------------------- | ------ | --- |
| `real_calls`                      | `calls - hook_calls`                                 | 扣掉插桩后剩余的 call 指令数，直接反映函数体发起调用的次数；coverage 一般不新增 call。注意 `__chkstk`、security cookie、EH 等运行时辅助调用仍计入 | **高**  | 已有  |
| `conditional_jumps`               | 条件跳转数（`jcc` 等）                                       | 直接对应 `if / for / while / switch` 等真实分支；当前构建的插桩和 coverage 基本不增加条件跳转。注意是静态计数，包含未执行的冷路径 | **高**  | 已有  |
| `decoded_bytes` / `decode_error`  | Capstone 实际解码的字节数，以及是否在 `size` 结束前停止                 | 直接反映反汇编覆盖是否完整；`decoded_bytes < size` 或 `decode_error` 为真时，其余反汇编字段都要降级      | **高**  | 已有  |
| `direct_calls` / `indirect_calls` | 直接目标 `call` 与寄存器/内存目标 `call` 的数量（含钩子调用）             | 操作数类型可直接判断；能区分普通转发和虚调用/函数指针                            | **高**  | 已有  |
| `size`                            | PDB 里的函数 code size，单位字节                              | 直接反映机器码体积；但包含插桩、coverage 和对齐填充，绝对值和跨函数比较都不可靠                            | 中高（仅相对） | 已有  |
| `rets`                            | `ret` 指令数                                            | 多个 return 通常意味着多出口/提前返回；插桩一般不改变 ret 数                                    | 中高     | 已有  |
| `last`                            | 函数最后一条指令的助记符                                         | 末尾 `jmp` 常见于尾调用/thunk；需要结合跳转目标和 `real_calls` 判断                           | 中高     | 已有  |
| `branchless`                      | `conditional_jumps == 0`                             | 直接由条件跳转数派生，反映“没有条件分支”；但空函数、纯顺序代码也满足                                     | 中高     | 已有  |
| `tail_thunk`                      | 首/末指令为 `jmp`，且 `tail_target_kind == direct_external` | 直接目标在函数外，能确认是真正的尾转发；本地 `jmp`（循环/汇合/收尾）不再计入。当前构建 0 命中 | **高**  | 已有  |
| `padding_bytes` / `trailing_pad`  | 函数末尾连续 `int3` / `nop` 的填充字节数，以及是否存在尾填充                | 能修正 `size` / `instructions` 的膨胀；只处理尾部填充，函数中间的合法 `int3`/`nop` 不扣减            | 中高     | 已有  |
| `runtime_calls`                   | 命中 `__chkstk`、`__security_check_cookie`、EH 辅助符号等的直接调用数   | 这些是编译器/运行时开销，不是函数逻辑；依赖已知辅助符号清单，可能漏判                                    | 中高     | 已有  |
| `logic_calls`                     | `real_calls - runtime_calls`                         | 比 `real_calls` 更接近函数体主动发起的调用；可信度取决于 `runtime_calls` 是否识别完整                 | 中高     | 已有  |
| `distinct_call_targets`           | 排除钩子后的静态直接 `call` 不同目标数（含运行时辅助）                    | 直接目标可精确计数，能区分“调用一次”和“只调用一个函数”；间接调用无法解析                               | 中高     | 已有  |
| `tail_target_kind`                | 末尾/首条 `jmp` 的目标类别：direct_local / direct_external / indirect / none | 直接目标可解析，能确认是否真正转发到另一个函数；间接目标只能标 `indirect`，无尾跳时为 `none`             | 中高     | 已有  |
| `stack_frame_bytes` / `push_count` | 整个函数内 `sub rsp` 的累计字节数和 `push` 指令数                   | 纯转发通常没有或只有极小栈帧；插桩会引入固定栈操作，只适合同批相对比较                                     | 中高     | 已有  |
| `basic_blocks` / `back_edges`     | 按直接跳转目标切分的基本块数和后向跳转数                                     | 比 `jumps` 更接近控制流复杂度；间接跳转和异常边未建模，可能低估                                    | 中高     | 已有  |
| `first_after_hook`                | 跳过首段 `__cyg_profile_func_*` 调用后的第一条指令                   | 排除钩子前导，比 `first` 更接近函数核心；coverage 计数指令仍可能排在它前面，需要结合其他字段                    | 中高     | 已有  |
| `hook_balance`                    | `{enter, exit, balanced}`，`balanced = enter == exit && enter > 0` | 能发现缺 enter/exit 或不对称插桩；本构建每个函数都是 1/1，因此这一项在当前数据上区分度低                      | 中高     | 已有  |
| `fp_simd_insns` / `lock_insns`    | FPU/MMX/SSE/AVX 等分组指令数，以及 `lock` 前缀或内存 `xchg` 数              | 出现即说明有真实计算或并发逻辑，几乎不会由插桩产生；仍需排除编译器生成的辅助代码                                | 中高     | 已有  |
| `instructions`                    | Capstone 从函数入口按 `size` 反汇编出的指令数                      | 与代码体积强相关；同样包含钩子、coverage 和填充，薄函数被固定开销抬高                                | 中（仅相对） | 已有  |
| `first`                           | 函数第一条指令的助记符                                          | 辅助判断 thunk/转发形态；插桩或 coverage 可能把前导指令放在前面，第一条不一定是核心指令                 | 中      | 已有  |
| `forwarder_candidate`             | `tiny && branchless && real_calls == 1 && rets >= 1` | 组合了几个相对可靠的信号，但阈值人为且会把极小真实函数（getter、时间戳函数）算进来                           | 中（候选）  | 已有  |
| `switch_tables`                   | 疑似 `switch` 跳转表分派点数量（0 表示没有）                      | 启发式：间接 `jmp` 前 10 条内出现带索引的表访存，并且有 `cmp`/`test` 或条件跳转；可能漏判或把其他间接跳转算进来        | 中      | 已有  |
| `rip_relative_refs` / `global_refs` | RIP 相对内存引用指令数 / 其中落在 `.rdata`、`.data`、`.tls` 的引用数 | 能区分“访问全局数据”和纯寄存器/栈操作；coverage 段引用已排除，但仍包含 IAT、字符串、跳转表等间接访问               | 中      | 已有  |
| `jumps`                           | 所有跳转指令数（含条件跳转、无条件跳转、循环回边、尾跳）                         | 能反映控制流，但无条件跳转和异常/清理跳转混在一起，单独看容易误判                                      | 中低     | 已有  |
| `calls`                           | 函数内所有 `call` 指令数                                     | 包含 `__cyg_profile_func_enter/exit`，每个函数至少有钩子调用，不能直接代表内部调用          | 低      | 已有  |
| `hook_calls`                      | 命中 `__cyg_profile_func_enter/exit` 的调用数              | 这是插桩污染本身的度量，不是函数逻辑；只用于扣减和判断污染程度                                        | 低（内部逻辑） | 已有  |
| `tiny`                            | `0 < size <= 128`                                    | 简单阈值，完全依赖被污染的 `size`；只能标记“可能很薄”                                    | 低      | 已有  |

中高及以上和“中”档的字段都已经写入 `disasm.json`；目前表内不再有
`待补` 字段。

## 2. 计时字段可信度

`timing.json` 里每个函数有 `count`、`total_self_ns`、`total_inclusive_ns`、
`mean_self_ns`、`mean_inclusive_ns`、`self_share`。

> 时间来自 QPC ticks，本次构建频率 10 MHz（1 tick = 100 ns）。
> `self` 是 measured self：包含本函数 enter/exit 钩子的 bookkeeping，
> 不包含 QPC 调用本身；没有被插桩的 callee 时间会留在 self 里。

| 字段                   | 说明                                   | 为什么可信 / 不可信                                                               | 可信度             |
| -------------------- | ------------------------------------ | ------------------------------------------------------------------------- | --------------- |
| `total_self_ns`      | 整个窗口内所有调用的 self 时间之和                 | 大函数可信；薄函数被钩子开销抬高；总时间还受调用次数影响，不能跨函数直接比较                                    | 中               |
| `total_inclusive_ns` | 所有调用的 inclusive 时间之和                 | 包含 callee 和钩子；主要反映 workload，不反映函数内部实现                                     | 中低              |
| `mean_self_ns`       | `total_self_ns / count`              | µs/ms 级可信；30–100ns 级基本是钩子地板，不能当函数体耗时；count 大才稳定                           | 中高（大函数）/ 低（薄函数） |
| `mean_inclusive_ns`  | `total_inclusive_ns / count`         | 包含 callee；适合同一 caller/callee 的对比，不适合判断内部复杂度                               | 中低              |
| `self_share`         | `total_self_ns / total_inclusive_ns` | 归一化后最适合相对判断：低 share 说明时间主要在 callee；但叶子函数 share = 1，未插桩 callee 会让 share 偏高 | 中高              |

补充：

- `count` 是精确调用次数，但异常/longjmp 可能少计；`mean_*` 依赖它，
  count 太小平均值不稳；
- 本次实测薄函数的地板约 **30 ns**；`BM_mesh_intersect` 的 `self_share`
  约 21%，`node_geo_exec` 约 0，叶子函数是 100%；
- 不要用不同函数的 `total_*` 直接比较；先看 `self_share`，再看
  `mean_self_ns` 和 `count`。

## 3. 调用图字段：出度

`only_call.json` 的口径是 **观测出度 == 1**：

```text
out_degree = 该函数在 edge.json 中出现过的不同 callee 数
only_call  = out_degree == 1
```

先区分三个概念：

- **出度**：这个函数调用了几个不同的函数；
- **入度**：这个函数被几个不同的 caller 调用（不是本卡片的含义）；
- **调用次数**：函数实际被调用了多少次（见 `timing.count`），不是出度。

| 字段                         | 说明                             | 为什么可信 / 不可信                    | 可信度    |
| -------------------------- | ------------------------------ | ------------------------------ | ------ |
| `out_degree`               | `edge.json` 中不同 callee 的数量     | 直接来自观测调用边；但分支没走到、callee 未插桩时会漏 | 中      |
| `only_call.meta.criterion` | 固定为 `observed_out_degree == 1` | 明确口径，不会和“入度 1”混淆               | 高（口径）  |
| `only_call.functions[]`    | 平铺 `{name,file,line}`          | 只包含当前窗口观测出度 1 的函数              | 中高（候选） |
| `only_call.meta.count`     | 数量                             | 精确计数                           | 高（计数）  |

当前 boolean 运行：

```text
函数总数 2,269
出度分布：0 -> 832，1 -> 675，2 -> 293，3 -> 152 ...
only_call：675 个
其中 source/ + intern/：610 个，非头文件：371 个
```

注意：

- 出度 1 **不等于**纯转发，真实函数也可能只调用一个 helper；
- 同一个 callee 被调用多次，出度仍然是 1；它不是调用次数；
- 这是动态观测：某个分支没走到时，静态上存在的其他 callee 不会出现；
- 没插桩的 callee 不会形成 edge，出度可能偏低，所以要和
  `functions[].disasm.real_calls` 一起看；
- “出度 == 1”不是“只被一个 caller 调用”（入度 == 1）。

## 4. 推荐判据

主判据（优先看这三个）：

```text
conditional_jumps == 0
real_calls == 1
tail_thunk == true（即 tail_target_kind == direct_external）或 size 很小
```

辅助判据：

```text
rets、size、instructions 用于排序和排除明显的大函数
```

不要单独使用：

```text
calls、hook_calls、tiny、jumps
```

纯转发候选的最终确认，分两种形态：

```text
A. 尾转发     tail_target_kind == direct_external
B. 调用包装   out_degree == 1              // only_call
              real_calls == 1              // disasm
              conditional_jumps == 0       // disasm
              self_share 接近 0            // timing
```

反过来，`real_calls == 0 && tail_target_kind != direct_external` 是叶子/
无调用函数（例如纯数学函数），不能因为“没有调用”或“看起来简单”就标成无用。

其中 `out_degree` 来自 `only_call.json`，`self_share` 来自 `timing.json`，
`real_calls` / `conditional_jumps` / `tail_target_kind` 来自 `disasm.json` 的
`functions[].disasm`。

## 5. 符号名

### 5.0 数据来源：PDB 提供名字，functions.bin 决定范围

符号名的权威来源是 **PDB**（CodeView），不是 exe 的机器码；
`functions.bin` 只提供本次运行实际插桩/进入过的函数 RVA，是报告的**总体**。
`disasm.json` 是两者的交集：

```text
PDB ──SymFromAddrW + SYMOPT_UNDNAME──► name / file / line / size
functions.bin ──u64 RVA──────────────► 被观测的函数集合
disasm.json = functions.bin 的 RVA 经 PDB 解析后的子集
```

当前 boolean 运行实测（PDB 用 `SymEnumSymbols` 全量枚举，disasm 用
`functions.bin` 的 2,330 个 RVA）：

| 项目 | PDB 全量函数符号 | disasm（functions.bin 子集） |
| --- | ---: | ---: |
| 函数符号记录 | 152,912 | 2,330 |
| `global_init` | 2,236 | 0 |
| `hook` | 2 | 0 |
| `deleting_destructor` | 2 | 0 |
| `thunk` | 0 | 0 |
| `normal` | 150,672 | 2,330 |

> PDB 的符号记录数大于函数地址数：同一 RVA 可能对应多个模板/别名符号；
> `disasm.json` 每个 RVA 只保留 `SymFromAddr` 返回的一条。

这张表说明：5.1 的规则在 **PDB 全量**上是有命中的，但 `disasm.json`
只覆盖被插桩且观测到的子集。编译器生成的 thunk、全局初始化函数和
hook 本体没有进入 `functions.bin`，所以 `symbol.kind` 在 `disasm.json`
里 2,330/2,330 全是 `normal`。

`name` 是 dbghelp 在 `SYMOPT_UNDNAME` 下返回的显示名，不是函数短名。
它仍然是全限定名，通常包含：

```text
namespace / class / method
模板实参：Foo<Bar<int>>
lambda：<lambda_1>、`lambda at <file>:<line>`
匿名命名空间：`anonymous namespace'::foo
构造/析构：Foo::Foo、Foo::~Foo
MSVC 代码生成标记：`dynamic initializer for 'x'`、
                    `dynamic atexit destructor for 'x'`、
                    `scalar deleting destructor`、[thunk]:
Itanium 代码生成标记：non-virtual thunk to、_GLOBAL__sub_I_...
```

同一份 PDB 可能混合两套 ABI 命名：Blender 自身是 Clang 构建（Itanium
风格），部分第三方/系统库是 MSVC 构建（MSVC 风格）。当前 PDB 中
MSVC 风格标记名 1,932 个，Itanium 风格标记名 9,059 个。

因此名字匹配必须用**子串 + 大小写不敏感**，不能假设只有一种 ABI；
`name` 相同也不一定是同一个函数（同一源码行的模板/lambda 可能有多个实例）。

`disasm.json` 每条记录的布局：

```text
functions[]
  name / file / line / module
  disasm { size, instructions, calls, ..., tail_thunk }
  symbol { kind, tags }
```

### 5.1 PDB 全量可按名字直接判断的

| 符号名模式                                                                                      | 含义                         | 可信度 / 用法                                    |
| ------------------------------------------------------------------------------------------ | -------------------------- | ------------------------------------------- |
| `[thunk]:`、`vcall`、`adjustor`、`non-virtual thunk to`、`virtual thunk to`                    | 编译器生成的 this 指针调整/虚调用 thunk | **高（PDB 全量层面）**：基本就是纯转发；当前 disasm 集合 0 命中 |
| `dynamic initializer`、`dynamic atexit destructor`、`_GLOBAL__sub_I`、`__cxx_global_var_init` | 全局对象初始化/清理                 | **高（不是业务逻辑）**：PDB 全量层面排除；当前 disasm 集合 0 命中 |
| `__cyg_profile_func_enter/exit`                                                            | 函数插桩钩子                     | **高**：纯 instrumentation；当前 disasm 集合 0 命中   |
| `deleting destructor`、`vector deleting destructor`                                         | 析构辅助函数                     | 高（编译器生成），但可能包含真实清理逻辑；当前 disasm 集合 0 命中 |

这些规则在 `disasm.py` 里有防御性实现，但**它们是对 PDB 全量符号的
分类规则，不能直接用于 disasm 候选筛选**：

- 5.1 混用了 MSVC 命名（`[thunk]:`、`vcall`、`adjustor`、
  `dynamic initializer`、`deleting destructor`）和 Itanium 命名
  （`non-virtual thunk to`、`_GLOBAL__sub_I`、`__cxx_global_var_init`）；
- 当前构建是 Clang，`name` 是去修饰后的全限定名；
- PDB 全量 152,912 个函数符号里，5.1 命中 `global_init` 2,236、
  `hook` 2、`deleting_destructor` 2，`thunk` 0；
- 但 `functions.bin` 只包含被插桩的函数，这些编译器生成符号和 hook 本体
  都不在集合里，所以 disasm 的 2,330 个函数全部是 `normal`；
- `[thunk]:` 和 `non-virtual thunk to` 在当前 PDB 里也是 0 命中，
  thunk 规则完全没有样本。

所以 `normal` 只表示“没有命中 5.1”，**不表示**“没有编译器生成物”，
也不表示“是业务逻辑”。筛选脚本不要依赖 `symbol.kind`。如果确实需要
按这些类别排除，应在 **PDB 全量符号**层面做（`SymEnumSymbols`），或者
让插桩覆盖这些函数；名字最多只能按 5.2 当弱提示。

| `symbol.kind`         | 命中的 `symbol.tags`                                                                   |
| --------------------- | ---------------------------------------------------------------------------------- |
| `thunk`               | `thunk`、`vcall`、`adjustor`、`non_virtual_thunk`、`virtual_thunk`                      |
| `global_init`         | `dynamic_initializer`、`dynamic_atexit_destructor`、`global_sub_i`、`cxx_global_var_init` |
| `hook`                | `hook`                                                                             |
| `deleting_destructor` | `deleting_destructor`、`vector_deleting_destructor`                                  |
| `normal`              | 空（没有命中任何 5.1 模式）                                                                  |

`meta.symbol_kinds` 给出各 `kind` 的数量，`meta.symbol_kinds_note` 记录
“normal ≠ 业务逻辑”这条限制。`deleting_destructor` 可能包含真实清理逻辑，
这里只记录名字类别，不做删除建议。

### 5.2 只能作为提示的

| 符号名模式                                                      | 含义            | 可信度 / 用法                       |
| ---------------------------------------------------------- | ------------- | ------------------------------ |
| `lambda at <file>:<line>`、`$_0`、`std::_Func_impl_no_alloc` | lambda / 回调包装 | 中低：可能是薄回调，也可能有真实逻辑，需看 `disasm` |
| `Foo<...>` 模板实参                                            | 模板实例化         | 低：可能是转发到通用实现，也可能就是实现本身         |
| `` `anonymous namespace' ``                                | 文件内局部函数       | 低：只说明可见性，不说明是否转发               |
| `BKE_`、`BLI_`、`RNA_`、`ED_` 等前缀                             | C API / 公共封装  | 低到中：常见“包装 C++ 内部实现”，但必须结合反汇编确认 |
| `std::`、`tbb::`、`fmt::`、`openvdb::` 等                      | 第三方/标准库       | 通常不在翻译范围；是否薄与业务无关              |

5.2 的等级都在“中”以下（中低/低/低到中），按“只收中以上”的原则
**不写入** `symbol`：`kind` 只由 5.1 分类，lambda、模板、匿名命名空间
和 C API 前缀的函数仍然是 `normal`，需要过滤时直接对 `name` 做匹配。
`normal / tags: []` 只表示“没有命中 5.1”，不是低可信分类。
