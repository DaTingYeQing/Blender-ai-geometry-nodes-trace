# 筛选

本手册记录把动态 trace 收敛成“纯转发 / 真实实现”候选时使用的判据。

## 1. 反汇编字段可信度

> 当前 `disasm.json` 来自带 `-finstrument-functions-after-inlining` 和
> coverage 的构建。`size` / `instructions` 包含插桩与 coverage 指令；
> `calls` 包含 `__cyg_profile_func_*` 调用；`real_calls` 已扣除这些钩子。
> 下表按可信度从高到低排列；`现状` 为 `已有` 的字段已经写入
> `functions[].disasm`，为 `待补` 的尚未产出。

可信度定义：

- **高**：接近函数内部逻辑，可以直接作为主判据；
- **中高**：有明确偏差或依赖启发式，适合相对比较和组合判断；
- **中**：受插桩、coverage、编译器生成代码影响较大，只能辅助；
- **中低**：多类信号混在一起，单独使用容易误判；
- **低**：主要反映插桩污染，不能代表函数逻辑。

| 字段                                | 说明                                                   | 为什么可信 / 不可信                                                             | 可信度    | 现状  |
| --------------------------------- | ---------------------------------------------------- | ----------------------------------------------------------------------- | ------ | --- |
| `real_calls`                      | `calls - hook_calls`                                 | 扣掉插桩后剩余的 call 指令数，直接反映函数体发起调用的次数；coverage 一般不新增 call。注意 `__chkstk`、security cookie、EH 等运行时辅助调用仍计入 | **高**  | 已有  |
| `conditional_jumps`               | 条件跳转数（`jcc` 等）                                       | 直接对应 `if / for / while / switch` 等真实分支；当前构建的插桩和 coverage 基本不增加条件跳转。注意是静态计数，包含未执行的冷路径 | **高**  | 已有  |
| `decoded_bytes` / `decode_error`  | Capstone 实际解码的字节数，以及是否在 `size` 结束前停止                 | 直接反映反汇编覆盖是否完整；`decoded_bytes < size` 或 `decode_error` 为真时，其余反汇编字段都要降级      | **高**  | 待补  |
| `direct_calls` / `indirect_calls` | 直接目标 `call` 与寄存器/内存目标 `call` 的数量                      | 操作数类型可直接判断；能区分普通转发和虚调用/函数指针                            | **高**  | 待补  |
| `size`                            | PDB 里的函数 code size，单位字节                              | 直接反映机器码体积；但包含插桩、coverage 和对齐填充，绝对值和跨函数比较都不可靠                            | 中高（仅相对） | 已有  |
| `rets`                            | `ret` 指令数                                            | 多个 return 通常意味着多出口/提前返回；插桩一般不改变 ret 数                                    | 中高     | 已有  |
| `last`                            | 函数最后一条指令的助记符                                         | 末尾 `jmp` 常见于尾调用/thunk；需要结合跳转目标和 `real_calls` 判断                           | 中高     | 已有  |
| `branchless`                      | `conditional_jumps == 0`                             | 直接由条件跳转数派生，反映“没有条件分支”；但空函数、纯顺序代码也满足                                     | 中高     | 已有  |
| `tail_thunk`                      | 首指令为 `jmp`，或末尾 `jmp` 且 `real_calls == 0`             | 能识别尾转发形态；当前只看助记符，不解析目标，无法区分本地跳转和外部转发                                | 中高     | 已有  |
| `padding_bytes` / `trailing_pad`  | 反汇编中识别出的 `int3` / `nop` 填充字节                         | 能修正 `size` / `instructions` 的膨胀；但合法 `int3`/`nop` 与对齐填充需要启发式区分            | 中高     | 待补  |
| `runtime_calls`                   | 命中 `__chkstk`、`__security_check_cookie`、EH 辅助符号等的调用数   | 这些是编译器/运行时开销，不是函数逻辑；依赖已知辅助符号清单，可能漏判                                    | 中高     | 待补  |
| `logic_calls`                     | `real_calls - runtime_calls`                         | 比 `real_calls` 更接近函数体主动发起的调用；可信度取决于 `runtime_calls` 是否识别完整                 | 中高     | 待补  |
| `distinct_call_targets`           | 静态直接 `call` 的不同目标数                                   | 直接目标可精确计数，能区分“调用一次”和“只调用一个函数”；间接调用无法解析                               | 中高     | 待补  |
| `tail_target_kind`                | 末尾 `jmp` 的目标类别：direct / indirect / local / external  | 直接目标可解析，能确认是否真正转发到另一个函数；间接目标只能标 `indirect`                             | 中高     | 待补  |
| `stack_frame_bytes` / `push_count` | prologue 中 `sub rsp` 的字节数和 `push` 数                   | 纯转发通常没有或只有极小栈帧；插桩会引入固定栈操作，只适合同批相对比较                                     | 中高     | 待补  |
| `basic_blocks` / `back_edges`     | 按跳转目标切分的基本块数和回边数                                     | 比 `jumps` 更接近控制流复杂度；间接跳转和异常边未建模，可能低估                                    | 中高     | 待补  |
| `first_after_hook`                | 跳过 `__cyg_profile_func_*` 调用后的第一条指令                   | 排除插桩前导，比 `first` 更接近函数核心逻辑；依赖钩子识别准确                                    | 中高     | 待补  |
| `hook_balance`                    | enter/exit 钩子调用是否配平                                  | 能发现尾调用、longjmp、漏插桩；正常多出口函数也会出现不配平，需要结合 `rets`                           | 中高     | 待补  |
| `fp_simd_insns` / `lock_insns`    | 浮点/SIMD 指令数，以及 `lock` 前缀/原子指令数                       | 出现即说明有真实计算或并发逻辑，几乎不会由插桩产生；仍需排除编译器生成的辅助代码                                | 中高     | 待补  |
| `instructions`                    | Capstone 从函数入口按 `size` 反汇编出的指令数                      | 与代码体积强相关；同样包含钩子、coverage 和填充，薄函数被固定开销抬高                                | 中（仅相对） | 已有  |
| `first`                           | 函数第一条指令的助记符                                          | 辅助判断 thunk/转发形态；插桩或 coverage 可能把前导指令放在前面，第一条不一定是核心指令                 | 中      | 已有  |
| `forwarder_candidate`             | `tiny && branchless && real_calls == 1 && rets >= 1` | 组合了几个相对可靠的信号，但阈值人为且会把极小真实函数（getter、时间戳函数）算进来                           | 中（候选）  | 已有  |
| `switch_tables`                   | 是否存在间接跳转表                                          | `switch` 结构提示；模式识别可能漏掉非标准跳转表或把其他间接跳转算进来                                | 中      | 待补  |
| `rip_relative_refs` / `global_refs` | RIP 相对内存引用/全局数据访问数                                  | 真实逻辑常读写全局数据；coverage 和插桩也会引入数据引用，必须过滤后再用                                | 中      | 待补  |
| `jumps`                           | 所有跳转指令数（含条件跳转、无条件跳转、循环回边、尾跳）                         | 能反映控制流，但无条件跳转和异常/清理跳转混在一起，单独看容易误判                                      | 中低     | 已有  |
| `calls`                           | 函数内所有 `call` 指令数                                     | 包含 `__cyg_profile_func_enter/exit`，每个函数至少有钩子调用，不能直接代表内部调用          | 低      | 已有  |
| `hook_calls`                      | 命中 `__cyg_profile_func_enter/exit` 的调用数              | 这是插桩污染本身的度量，不是函数逻辑；只用于扣减和判断污染程度                                        | 低（内部逻辑） | 已有  |
| `tiny`                            | `0 < size <= 128`                                    | 简单阈值，完全依赖被污染的 `size`；只能标记“可能很薄”                                    | 低      | 已有  |

## 2. 计时字段可信度

`timing.json` 里每个函数有 `count`、`total_self_ns`、`total_inclusive_ns`、
`mean_self_ns`、`mean_inclusive_ns`、`self_share`。

> 时间来自 QPC ticks，本次构建频率 10 MHz（1 tick = 100 ns）。
> `self` 是 measured self：包含本函数 enter/exit 钩子的 bookkeeping，
> 不包含 QPC 调用本身；没有被插桩的 callee 时间会留在 self 里。

| 字段                   | 说明                                   | 为什么可信 / 不可信                                                               | 可信度             |
| -------------------- | ------------------------------------ | ------------------------------------------------------------------------- | --------------- |
| `total_self_ns`      | 整个窗口内所有调用的 self 时间之和                 | 大函数可信；薄函数被钩子开销抬高；总时间还受调用次数影响，不能跨函数直接比较                                    | 中               |
| `total_inclusive_ns` | 所有调用的 inclusive 时间之和                 | 包含 callee 和钩子；主要反映 workload，不反映函数内部实现                                     | 中低              |
| `mean_self_ns`       | `total_self_ns / count`              | µs/ms 级可信；30–100ns 级基本是钩子地板，不能当函数体耗时；count 大才稳定                           | 中高（大函数）/ 低（薄函数） |
| `mean_inclusive_ns`  | `total_inclusive_ns / count`         | 包含 callee；适合同一 caller/callee 的对比，不适合判断内部复杂度                               | 中低              |
| `self_share`         | `total_self_ns / total_inclusive_ns` | 归一化后最适合相对判断：低 share 说明时间主要在 callee；但叶子函数 share = 1，未插桩 callee 会让 share 偏高 | 中高              |

补充：

- `count` 是精确调用次数，但异常/longjmp 可能少计；`mean_*` 依赖它，
  count 太小平均值不稳；
- 本次实测薄函数的地板约 **30 ns**；`BM_mesh_intersect` 的 `self_share`
  约 21%，`node_geo_exec` 约 0，叶子函数是 100%；
- 不要用不同函数的 `total_*` 直接比较；先看 `self_share`，再看
  `mean_self_ns` 和 `count`。

## 3. 调用图字段：出度

`only_call.json` 的口径是 **观测出度 == 1**：

```text
out_degree = 该函数在 edge.json 中出现过的不同 callee 数
only_call  = out_degree == 1
```

先区分三个概念：

- **出度**：这个函数调用了几个不同的函数；
- **入度**：这个函数被几个不同的 caller 调用（不是本卡片的含义）；
- **调用次数**：函数实际被调用了多少次（见 `timing.count`），不是出度。

| 字段                         | 说明                             | 为什么可信 / 不可信                    | 可信度    |
| -------------------------- | ------------------------------ | ------------------------------ | ------ |
| `out_degree`               | `edge.json` 中不同 callee 的数量     | 直接来自观测调用边；但分支没走到、callee 未插桩时会漏 | 中      |
| `only_call.meta.criterion` | 固定为 `observed_out_degree == 1` | 明确口径，不会和“入度 1”混淆               | 高（口径）  |
| `only_call.functions[]`    | 平铺 `{name,file,line}`          | 只包含当前窗口观测出度 1 的函数              | 中高（候选） |
| `only_call.meta.count`     | 数量                             | 精确计数                           | 高（计数）  |

当前 boolean 运行：

```text
函数总数 2,269
出度分布：0 -> 832，1 -> 675，2 -> 293，3 -> 152 ...
only_call：675 个
其中 source/ + intern/：610 个，非头文件：371 个
```

注意：

- 出度 1 **不等于**纯转发，真实函数也可能只调用一个 helper；
- 同一个 callee 被调用多次，出度仍然是 1；它不是调用次数；
- 这是动态观测：某个分支没走到时，静态上存在的其他 callee 不会出现；
- 没插桩的 callee 不会形成 edge，出度可能偏低，所以要和
  `functions[].disasm.real_calls` 一起看；
- “出度 == 1”不是“只被一个 caller 调用”（入度 == 1）。

## 4. 推荐判据

主判据（优先看这三个）：

```text
conditional_jumps == 0
real_calls == 1
tail_thunk == true 或 size 很小
```

辅助判据：

```text
rets、size、instructions 用于排序和排除明显的大函数
```

不要单独使用：

```text
calls、hook_calls、tiny、jumps
```

纯转发候选的最终确认，建议同时满足：

```text
out_degree == 1              // only_call
real_calls == 1              // disasm
conditional_jumps == 0       // disasm
self_share 接近 0            // timing
```

其中 `out_degree` 来自 `only_call.json`，`self_share` 来自 `timing.json`，
`real_calls` / `conditional_jumps` 来自 `disasm.json` 的
`functions[].disasm`。

## 5. 符号名

所有 JSON 里的 `name` 都是 PDB 的 **undecorated symbol name**，不是简单的
函数短名。它通常包含：

```text
namespace / class / method
模板实参：Foo<Bar<int>>
lambda 位置：`lambda at <file>:<line>`
匿名命名空间：`anonymous namespace'::foo
编译器生成标记：[thunk]:、vcall、adjustor、non-virtual thunk to
构造/析构：Foo::Foo、Foo::~Foo、deleting destructor
静态初始化：dynamic initializer、_GLOBAL__sub_I_...
```

`disasm.json` 每条记录的布局：

```text
functions[]
  name / file / line / module
  disasm { size, instructions, calls, ..., tail_thunk }
  symbol { kind, tags }
```

### 5.1 可按名字直接判断的

| 符号名模式                                                                                      | 含义                         | 可信度 / 用法                     |
| ------------------------------------------------------------------------------------------ | -------------------------- | ---------------------------- |
| `[thunk]:`、`vcall`、`adjustor`、`non-virtual thunk to`、`virtual thunk to`                    | 编译器生成的 this 指针调整/虚调用 thunk | **高**：基本就是纯转发，可直接排除或标记       |
| `dynamic initializer`、`dynamic atexit destructor`、`_GLOBAL__sub_I`、`__cxx_global_var_init` | 全局对象初始化/清理                 | **高（不是业务逻辑）**：静态翻译时直接排除      |
| `__cyg_profile_func_enter/exit`                                                            | 函数插桩钩子                     | **高**：纯 instrumentation，必须排除 |
| `deleting destructor`、`vector deleting destructor`                                         | 析构辅助函数                     | 高（编译器生成），但可能包含真实清理逻辑         |

这些规则已经写进 `disasm.json`：

| `symbol.kind`         | 命中的 `symbol.tags`                                                                   |
| --------------------- | ---------------------------------------------------------------------------------- |
| `thunk`               | `thunk`、`vcall`、`adjustor`、`non_virtual_thunk`、`virtual_thunk`                      |
| `global_init`         | `dynamic_initializer`、`dynamic_atexit_destructor`、`global_sub_i`、`cxx_global_var_init` |
| `hook`                | `hook`                                                                             |
| `deleting_destructor` | `deleting_destructor`、`vector_deleting_destructor`                                  |
| `normal`              | 空（没有命中任何 5.1 模式）                                                                  |

`meta.symbol_kinds` 给出各 `kind` 的数量。`deleting_destructor` 可能包含
真实清理逻辑，这里只记录名字类别，不做删除建议。

### 5.2 只能作为提示的

| 符号名模式                                                      | 含义            | 可信度 / 用法                       |
| ---------------------------------------------------------- | ------------- | ------------------------------ |
| `lambda at <file>:<line>`、`$_0`、`std::_Func_impl_no_alloc` | lambda / 回调包装 | 中低：可能是薄回调，也可能有真实逻辑，需看 `disasm` |
| `Foo<...>` 模板实参                                            | 模板实例化         | 低：可能是转发到通用实现，也可能就是实现本身         |
| `` `anonymous namespace' ``                                | 文件内局部函数       | 低：只说明可见性，不说明是否转发               |
| `BKE_`、`BLI_`、`RNA_`、`ED_` 等前缀                             | C API / 公共封装  | 低到中：常见“包装 C++ 内部实现”，但必须结合反汇编确认 |
| `std::`、`tbb::`、`fmt::`、`openvdb::` 等                      | 第三方/标准库       | 通常不在翻译范围；是否薄与业务无关              |

5.2 的等级都在“中”以下（中低/低/低到中），按“只收中以上”的原则
**不写入** `symbol`：`kind` 只由 5.1 分类，lambda、模板、匿名命名空间
和 C API 前缀的函数仍然是 `normal`，需要过滤时直接对 `name` 做匹配。
`normal / tags: []` 只表示“没有命中 5.1”，不是低可信分类。
